Methodology & Limitations

Important: all bias findings on this site come from documented mechanisms built into the simulation, listed in the assumptions table below. They are not measurements of the real Aadhaar system. The value of the project is to show how such mechanisms turn into measurable exclusion, and how fairness metrics detect it.

1. How the data was generated

A seeded Python script (data/generate_aadhaar_auth_dataset.py) creates {{ kpis.total_beneficiaries|thousands }} invented beneficiaries. Each makes {{ assumptions.visits_per_beneficiary }} visits; each visit allows up to {{ assumptions.max_attempts_per_visit }} attempts, giving {{ kpis.total_visits|thousands }} visits and {{ kpis.total_attempts|thousands }} attempts. For every attempt the script:

  1. Computes a capture quality (0-100) from occupation, device, environment and age, plus random noise at person, visit and attempt level. Iris quality ignores occupation, environment and age.
  2. Checks for a network timeout, then a device error. These stop the attempt with no match score.
  3. Computes a match score that rises with quality for genuine users and stays low for impostors.
  4. Rejects captures below quality {{ assumptions.min_capture_quality }} as Poor quality capture, and scores below {{ "%.2f"|format(threshold) }} as Biometric mismatch.

Note on the generator file: the original generator script was not available, so this one was reconstructed and calibrated (by regression and cross-tabulation) to reproduce the patterns in the supplied CSV. The dashboard analyses the original CSV unchanged; the reconstructed generator drives the Simulator and documents the assumptions. Re-running it gives a statistically similar dataset, not an identical one.

3. Metric definitions

MetricDefinitionPopulation
False Rejection Rate (FRR)Rejected attempts ÷ all attemptsGenuine users only
False Acceptance Rate (FAR)Accepted attempts ÷ all attemptsImpostors only
Attempt failure rateFailed attempts ÷ all attemptsEveryone
Denial rateVisits where every attempt failed ÷ visits (one row per session_id) Genuine visits for bias analysis (blocking an impostor is not exclusion)
Biometric vs system failureMismatch + poor capture vs network timeout + device errorKept separate throughout
Disparity ratioGroup denial rate ÷ best group's denial rateGenuine visits
Four-fifths rule (adapted)FAIL if disparity ratio > {{ "%.2f"|format(limit) }} (= 1 ÷ 0.8)Genuine visits
Chi-square testTests whether denial is independent of the attribute; p < 0.05 = significantGenuine visits
Odds ratioFrom a logistic regression of first-attempt failure; > 1 raises the odds vs the reference groupGenuine first attempts

4. Limitations

  • Synthetic data: every effect size was chosen by the modeller; the real system's numbers may differ.
  • Assumed bias is found bias: the analysis recovers the mechanisms put in; it cannot discover new ones.
  • Reconstructed generator: the simulator follows calibrated, not original, assumptions.
  • Small groups: 75+ and iris users are small samples, so their rates are less precise.
  • Simplified matching: real systems use fusion of multiple fingers, best-finger detection and OTP fallbacks.
  • No time dimension: device upgrades, outages and seasonal effects are not modelled.
  • Model: logistic regression assumes additive effects on the log-odds and ignores within-person correlation.

5. Recommendations

  • Fallback authentication: OTP to a registered mobile, iris, or a documented manual override by the dealer/officer so no one leaves without their entitlement.
  • Better devices: replace low-quality scanners first in rural and remote areas, where they are concentrated.
  • Offline mode: allow local or deferred authentication when the network is down, with later reconciliation.
  • Exception handling: automatic exemption or alternative proof for people aged 75+ and manual workers with worn fingerprints.
  • Monitoring: publish FRR and denial rates by age, occupation and area, and apply the four-fifths check routinely.
